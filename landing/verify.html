Verify this client

By JELL, Wymber · Last updated 2026-08-09

Wymber is open source, so anyone can host a copy of it. That's good for durability: your data outlives us, because the code to open a .wymber file will always be public, even if this site disappears one day. The same openness means the official client should be checkable, not just trusted. This page explains how, in plain language, and what checking it can and can't tell you.

The one thing that actually protects you

Only unlock Wymber at an address you typed or bookmarked yourself: wymber.app or web.wymber.app. Never enter your Wymber password or recovery code on any other site, no matter how convincing it looks, and no matter who sent you the link. If you remember nothing else from this page, remember that. It's the one step that protects you, whether or not you ever check anything below.

Everything past this point is for people who want to go further: technical checks that make the official client verifiable, rather than something you're just asked to trust.

What's running right now

Every build of the app carries a build stamp you can see with tools already in your browser, no downloads needed. Open the app at web.wymber.app, then View Source or open your browser's developer tools. Near the top of the page you'll find a line like:

<meta name="wymber-build" content="927914a">

Those seven characters are the exact commit in the public repository the app was built from. In the same source you'll also see an integrity="sha384-..." attribute on the main stylesheet and script tags, and a <script type="importmap"> block listing a hash for every module the app loads. Those hashes are how the browser itself refuses to run a file that doesn't match what was built, a modified module simply fails to load rather than running quietly changed.

Check it against the published hashes

The build stamp tells you what commit is running. To check the files themselves, compare the hashes published from two different places:

  1. Open web.wymber.app/integrity-manifest.json, the app's own origin. It's rewritten on every deploy, so it always describes exactly what's live there right now.
  2. Open wymber.app/integrity-manifest.json, this site's origin, a separate server. This copy is a deliberate release snapshot, so it may trail the app's copy by a small commit or two between releases, that's expected, not a problem by itself.
  3. Compare the two: the commit field, and the sha384- hash listed for any file you care about. When they agree, that's tamper-evidence that neither origin has been altered on its own: if someone changed a file served from just one of them, the two manifests would stop matching.

Check a copy you already have

Nothing you choose below is uploaded anywhere. Your browser reads the files, hashes them with the Web Crypto API, and compares the result to the list published on this page. This page makes no network requests at all: not before you start, not while it works, and not after.

There's no option to paste a web address instead. A tool that checks a site by fetching it from its own server can be shown one version while everyone else is served another, because the addresses that kind of check calls from are knowable ahead of time. It would then return a calm, confident pass on exactly the situation it exists to catch. The honest version of that check has to run in your own browser, against the bytes your own browser actually received: that's a bigger piece of work, tracked as issue #115.

This compares a copy of the app at web.wymber.app, the address people actually unlock at. wymber.app, where you are right now, only hosts this page and the list it checks against.

One difference is expected rather than worrying: the list here is a release snapshot, so it can trail the app by a commit or two. Every build stamps which commit it came from into index.html and build-info.js, so a copy built from a different commit will show those two as differing even when nothing is wrong. Check the commit each one names before reading anything into it.

Reproduce the build yourself

If you're comfortable with a terminal, you can build the exact commit named in the stamp and compare the result byte for byte:

git clone https://github.com/Tamok/wymber.git
cd wymber
git checkout <the commit from the build stamp>
node scripts/build-pages.mjs

That writes a fresh dist/ folder, including its own integrity-manifest.json, computed the same way the deployed one was. Compare it against the manifest published from either origin above. A match means the files being served are exactly the audited source at that commit.

A signed, append-only log (not active yet)

There's also a mechanism for the person who runs Wymber to sign each published manifest with a private key only they hold, and record that signature in an append-only, tamper-evident log alongside the manifest itself. We're documenting it here honestly, in advance: as of this writing, no signing key has been published, and the log is empty. Nothing described below is active yet. When it is, this page will say so plainly, and this paragraph will change.

Once a key exists, checking a release will look like this. Download the log from this site and the manifest from the app's origin, the same cross-origin idea as the hash comparison above, then verify them together with the same script that's already in the repository:

curl -o integrity-log.jsonl https://wymber.app/integrity-log.jsonl
curl -o integrity-manifest.json https://web.wymber.app/integrity-manifest.json
node scripts/integrity-log.mjs --log integrity-log.jsonl --manifest integrity-manifest.json --key <the published key>

The published key itself is meant to come from more than one place independent of this site, so that trusting it doesn't just mean trusting wymber.app a second time. A DNS record and this page's own repository are the two planned sources; details will land here once a real key exists. Full reasoning, including the parts we chose not to build yet and why, is in ADR-0007.

What this does not prove

Being honest about the limits matters as much as the checks themselves:

  • A web page can never prove its own honesty. A fake copy could show a build stamp, "verified" badge, or hash listing every bit as convincingly as the real one, so nothing on this page, or in the app itself, is proof by itself.
  • These checks cover the official deploy, wymber.app and web.wymber.app. They say nothing about a look-alike hosted somewhere else, which is exactly why the one rule above matters more than any check on this page.
  • If the build pipeline that produces both manifests were itself compromised, both origins would agree with each other and both would still be wrong. Agreement rules out one origin being tampered with alone; it isn't proof of the whole pipeline.
  • A signed log, once it exists, will not stop a compromised site from serving different files to one targeted person in the moment it happens. What it changes is what happens afterward: it makes that act provable, later, by someone else, rather than impossible.
  • A compromised release process would sign whatever it was told to build. A valid signature says the keyholder endorsed a file, not that the file is safe.

Work already underway points toward stronger, out-of-band ways to check this, without promising dates: unlocking with a passkey, which is bound to this site's address and simply can't be used on a look-alike; a signed desktop app as the highest-trust option; and an independent, out-of-band way to confirm the loaded code matches what's published. This page will grow to describe those as they land.
